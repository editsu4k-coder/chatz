# Firebase Operations Stress Test Report

## Purpose

Document expected Firestore operations generated by key user flows to establish baselines for optimization and verify that backend usage is predictable and bounded.

**Note:** These are theoretical counts based on code inspection. Actual measurements require the DEBUG counter enabled (see `DEBUG-FIREBASE-OPS.md`).

---

## User Flow: Opening Home Screen (Pulse)

### Initial Mount

| Operation | Count | Source |
|-----------|-------|--------|
| Read: users/{uid} | 1 | Profile load (cached after first load) |
| Read: friendRequests (incoming) | 1 query | Pending requests check |
| Read: friendships (array-contains) | 1 query | Friend list load |
| Read: users/{uid} × N friends | N | Profile resolution for each friend |
| Listener: usageStats/{uid} | 1 | Own stats sync timestamp |
| Listener: notifications (toUid == uid, limit 50) | 1 | Notification feed |
| Listener: chats (members array-contains uid) | 1 | DM overview for unread badges |
| Listener: usageStats/{friendUid} × M | M (max 8) | FriendCard live stats subscriptions |

**Total listeners on Home:** 3 + M (where M = number of visible friend cards, max 8)

**Optimization applied:** Notification query limited to 50 with orderBy (was unlimited lifetime).

## User Flow: Rapidly Tapping Comment Send (Spam Test)

**Without cooldown:** Could send 10+ comments in 5 seconds.

**With 2s cooldown (implemented):** Maximum 1 comment per 2 seconds. Button disabled during submission + timestamp check prevents bypassing via rapid clicks.

**Expected ops:** 1 write per 2 seconds maximum.

## User Flow: Sending a Friend Request

| Operation | Count | Source |
|-----------|-------|--------|
| Read: friendships/{uid}_{targetUid} | 1 | areFriends() check |
| Read: friendRequests/{uid}_{targetUid} | 1 | Check existing request |
| Write: friendRequests/{uid}_{targetUid} | 0-1 | setDoc or updateDoc (no-op if already pending) |
| Write: notifications/{autoId} | 0-1 | pushNotif() only if request actually created |

**Rate limiting:** Client-side 5-second cooldown between distinct requests (localStorage). Server-side: rules enforce senderId == auth.uid but don't rate-limit across targets.

**Expected ops:** 2 reads + 0-2 writes per request.

## User Flow: Background Statistics Sync (WorkManager)

### Every 15 Minutes (when conditions met)

| Scenario | Reads | Writes | Notes |
|----------|-------|--------|-------|
| Stats unchanged (local fingerprint match) | 0 | 0 | **Optimization applied:** Skip SERVER read entirely |
| Stats changed, server matches local | 1 | 0 | Fingerprint dedup at server level |
| Stats changed, server differs | 1 | 1 | Upload new snapshot |
| Silent mode | 0 | 0 | Worker exits early |
| No usage access | 0 | 0 | Worker exits early |
| Not signed in | 0 | 0 | Worker exits early |

**Optimization applied:** Local fingerprint cache in SharedPreferences prevents unnecessary SERVER reads when stats haven't changed since last upload.

**Expected average:** ~0.5 reads per 15-min interval (assuming stats change ~50% of the time).

## Remaining Risks (Server-Side Protection Needed)

These cannot be fully mitigated client-side and require Cloud Functions or enhanced Firestore rules:

1. **DM spam from modified APK:** 2s cooldown can be bypassed
2. **Comment flooding from modified APK:** 2s cooldown can be bypassed
3. **Friend request spam to different users:** 5s cooldown can be bypassed; no server-side rate limit across targets
4. **Reaction spam:** Mitigated by deterministic doc IDs (overwrites same doc), but still allows rapid toggling

**Recommendation:** For high-risk operations, implement Cloud Functions with rate limiting based on Firebase Auth context and Firestore timestamps.

## Measurement Instructions

To measure actual operations:

1. Enable debug mode: `window.__CHATZ_DEBUG_FIREBASE_OPS = true`
2. Perform the user flow
3. Run `printDebugReport()` to see counts
4. Compare against theoretical counts above
5. Verify active listeners return to baseline after navigation

**Expected baseline on Home screen:** 3 + M active listeners (M = visible friend cards, max 8)
**Expected baseline on other screens:** 1-3 active listeners (notifications + chats overview)
